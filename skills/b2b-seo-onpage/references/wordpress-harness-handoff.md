# 与 WordPress Build Harness 协作

用于已有 WordPress 项目的页面优化，或用户明确要求配合 Build Harness 实施。这里定义 SEO 与 WordPress 的交接；具体命令、字段与恢复步骤以本机实际 Harness、当前站点入口及已安装插件为准。不要复制一份 Harness、另建部署器，或把作者机器上的路径当用户环境。

## 分工与继续工作的责任

| 工作 | 负责的 Skill | 带入及带回的信息 |
| --- | --- | --- |
| 关键词、意图、竞品、事实核对、页面简报、Title/正文改稿 | `b2b-seo-onpage` | 保留主词、页型、事实来源、可用文案与资料缺口；不擅自决定数据库字段或部署方式 |
| 确定站点、local/live 目标、source/external 模式、编辑归属和执行路径 | `wordpress-builder` | 从实际项目入口和运行状态定位目标，选择下一责任方，沿用已有授权和进度 |
| 原生正文、已有 ACF 值、图片/链接、已有单页 SEO 值 | `wordpress-content` | 核字段和记录、保存原值、通过支持的适配器更新；返回相同 ID 的保存和字段回读证据 |
| PHP 模板、实际 H 标签、模块结构或绑定、新字段与模板组合 | `wordpress-design` | 只处理文案落实所需的代码/模型缺口，保留 CMS 可编辑性及页面现有风格；完成后回到未完成的页面修改 |
| 改后页面、原生编辑保存重开、必要的代码更新与目标验收 | `wordpress-delivery` | 核已保存内容与实际原始 URL 输出，区分本地、草稿预览、线上；将结果交回同一 On-page 任务 |
| 工具、依赖、连接或项目环境确实缺失 | `wordpress-setup` | 只修复当前阻碍，完成后回到原页面；不因接续优化而重新建站、导入内容或开通主机 |

Content 负责实施中的原生保存/字段回读，Delivery 汇总并补齐本次所需的目标页面验收；不把同一检查机械重跑两次。模板与字段模型的组合改动由 Design 持有到完成，必要时咨询 Content，不来回转交。最终仍由当前任务交付完整结果。

两种入口使用同一套分工：

- **从 Harness 开始**：Builder 已选定 Content/Design 和目标站点时，当前负责人调用本 Skill 取得 SEO 判断、简报和可用改稿，再沿原 Harness 操作继续。咨询 SEO 不转移站点实施责任，不重新初始化，也不把已确认的目标/字段/权限再问一遍。
- **从 On-page 开始**：先研究和形成改稿；需要 WordPress 实施时，通过 Builder 找到该项目原有负责人和适配器。把改稿映射与依据交过去，接回保存/验收结果，完成原任务。

“调用 Skill”表示 Codex 读取实际安装的入口及本次需要的参考文件并继续执行；不是让用户另发一轮提示词，也不是假定存在一个与 Skill 同名的命令。已有人负责当前阶段时，引用所需专业能力即可；仅在任务归属改变时正式转交。

## 1. 从当前项目接续

先读用户指定网站目录或当前目录的 `AGENTS.md`、它链接的当前摘要（常见为 `docs/CURRENT.md`）、`project.json`，按其中的 CLI/Router 指针定位实际 Harness。没有项目指针时，核环境中 `wordpress-builder` 的安装位置及其真实目标。读取实际 Router 的项目、模式与分工说明；按需加载相关 Skill，不要求用户记命令或再填一套项目表。

由这些材料和只读检查确定：本次目标 URL/记录、本地还是线上、源码与模板归属、现有编辑方式、已授权的修改范围。页面 slug、WordPress 记录标题、SEO Title 和可见 H1 是不同信息；本地与线上同一页面的数字 ID 也可能不同。

如果只交 SEO 简报/改稿，继续完成研究即可。用户已要求在明确的 WordPress 目标实施，就复用该授权继续。仅提供公网 URL 或要求给建议，不自动扩大成上线写入。已有站点继续原项目，不重新初始化 Starter。找不到 Harness/项目或无法确认目标时，保留可完成的研究与改稿，只询问实际缺失的项目位置或执行目标；不假装实施完成，也不擅自换成另一套连接方式。

## 2. 把“改哪里”落实为实际内容来源

读取原页面、当前记录和实际渲染模板后，在既有改稿表或项目记录里补充映射。只有跨会话/责任方交接需要独立文件时，再写 `wordpress-handoff.md`。这些信息由 Codex 查明和整理，用户不填写 JSON。

映射至少能回答：哪一条 SEO 改稿（可复用 `change_id`），对应哪个目标记录/路由，原值在哪里，建议写入哪个真实字段/模板，谁执行，以及怎样验证。复用主词、市场、业务事实、简报和现有改稿；不要让下一 Skill 重做选词或重新索要资料。

| SEO 改稿位置 | 必须先确认的 WordPress 来源 |
| --- | --- |
| SEO Title / description | 实际 SEO 输出负责人及该记录的覆盖值；Harness 默认新站使用 Rank Math，既有项目按实际状态检查 |
| H1 / H2 / 介绍段 | 可能来自 `post_title`、主编辑器、某个 ACF 值或 PHP 模板；修改显示文案与修改 HTML 标签是两类动作 |
| 产品/类目底部说明、采购指南、FAQ | 本项目的 WYSIWYG/Repeater/正文字段及真实模板绑定；不能把内容写进前台不读取的主编辑器 |
| 类目页面 | 区分 taxonomy term 与关联的 Page/CPT 内容页；查实际对应关系，不能默认写 term description |
| 产品卡/参数/媒体/内链 | 保留实际产品、分类和附件关联；产品查询生成的列表不复制成另一份硬编码内容 |

改 ACF 嵌套值时保留本次未改的其他字段、媒体和关联，按实际字段键及保存合同处理。需要新增模块/字段或把 H2 改成 H3 时，由 Design 确认模板影响和编辑器绑定，不能把 HTML 标签塞进纯文本字段充当模板修改。已有有效文案可保留。

只把本次可用的改稿纳入写入；未核实参数、认证、产能、交期等留在待核说明中。显式授权的内部模拟可在隔离本地演示中展示模拟文案，但继续保留 simulation/internal_only 身份，不能转成真实站点的公开事实。

## 3. 使用 Harness 当前支持的执行路径

选择命令前读取实际 Harness 的命令表和 Content 适配器说明。例如，下列命令用于查看合同，并不实施 SEO：

```sh
node "<HARNESS_ROOT>/wordpress-builder.mjs" commands --json
```

- **已有字段/正文**：按 Content 的现有适配器处理。实际 REST schema 暴露且允许写的字段可用其 `content-type` / `read-content` / `content-plan` / `content-apply`；保存既有记录要保留版本/指纹检查和原任务回执。未暴露的 ACF、分类关联或元数据用当前项目支持的原生适配器、原生后台，或已配置并获准的 SSH/WP-CLI 路径。不要仅为一次 SEO 修改暴露隐藏字段或新装连接插件。
- **本地 WordPress**：按 Setup 的现有本地预览合同启动/复用该项目，等待本次 readiness 回执，再通过对应本地客户端或后台实施。本地客户端入口为 `scripts/lab-wp.mjs --project <SITE_ROOT> ...`，后面是已支持的 REST 客户端命令；它不是远程 WP-CLI 的替代语法。本地优化不要求 Hostinger/SSH，不向远端发送写入。
- **模板/代码**：转 Design 修复实际归属的源码。需要线上更新时，由 Delivery 选择已授权的代码范围；纯字段值更新不触发完整部署、全站 seed 或数据库覆盖。
- **结果未知或冲突**：等待原操作结束，用原回执和目标 ID 先读实际保存状态，再按 Harness 的恢复合同继续；不换任务键重发一次或重建记录。

`onpage.py check-plan` 的 `plan.json` 记录研究、事实和改稿，它不是 Harness REST `content-plan` 的输入结构。实施方必须按真实字段映射生成对应适配器的请求，不能直接把 SEO 计划文件送去写库。canonical CLI、REST helper 与本地客户端也是不同接口；以实际 `commands --json` 和所选 Skill 文档为准，不发明 `seo update` 等子命令。

## 4. 单页 SEO 与全站配置分开

Rank Math 的单页标题/摘要、WordPress 记录标题、H1 及主题站点标题并不互相等价。由 Content 查实际插件字段、后台或当前支持的原生更新方式；即使字段已保存，仍需看模板/filter 是否覆盖了最终输出。只有已核实存在且可写的 meta 才能进入 REST 请求，不猜字段名和写入权限。

`configure-seo` 是 Harness 的站点/类型配置与验收能力，`configure-seo --release` 涉及正式开放索引；两者都不是单页 Title/description 改稿的默认执行器。普通 On-page 保留全站/单页 robots、canonical、sitemap、站点 URL、固定链接和既有 SEO 插件。若目标确实是修复这些问题，说明实际影响并走相应的已授权范围。不要安装第二个 SEO 插件、往主题再塞一份 title/meta，或为局部改稿重跑 SEO 初始化。

同样不因修改一段正文而重测邮件、重建表单或重做全站设计。保留相关模块/询盘路径；改动实际影响到它们时，再由对应 Skill 做必要验证。

## 5. 在真实目标闭环

保存后由 Content/Design 带回实际对象 ID、变更值/文件、原值恢复依据及未完成项，Delivery 按本次影响核验：

1. 重读相同记录的精确字段、状态、模板及相关关联；需要原生编辑验收时，后台保存完成后重开同一记录确认。API 成功不代表后台能保存重开。
2. 读取对应 WordPress 原始 URL；草稿用授权预览。本地访问本地 URL，不把另存 HTML 或未绑定的静态预览当网站已改好。
3. 核实际 `<title>`、description、可见标题与 H 标签、正文、链接/图片，以及本次要求保留的模块。元数据应只有实际负责方输出，不能以字串在页面某处出现代替正确位置。
4. 只有读到旧缓存时，按目标站现有接口清受影响缓存再复核，不默认清全站或其他项目。保存、前台、Google 展示和 SEO 效果分别记录。
5. 把实际改后 HTML/DOM 作为新的 On-page 证据，可用 `inspect` / `compare` 辅助对照；这些工具的快照匹配不替代 WordPress 字段、后台和前台验收。原 SEO 计划仍是 proposed，实际实施结果写入已有项目记录/回执。

最终用户只需要一个入口：本页改了什么、为何这样改、已经保存到哪里、实际查看地址、哪些内容还待确认。完整稿件与证据表可从这里打开；不要只给一堆内部路径、命令或让用户另开任务接力。交接沿用同一页面、资料、授权及未完成步骤，具体证据与限制如实说明。
